# Data Plan

The public catalog (videos, categories, models, channels, tags) is built into the client as the site's starting content. Everything the admin panel manages is the site owner's own data, stored in the artifact's database through its actions:

- `interactions` table — viewer likes, saves, follows and watch history (getState / toggleInteraction / recordHistory / clearHistory).
- `admin_state` table (single row, JSON payload) — admin panel state saved via getAdminState / saveAdminState / resetAdminState: editable site texts, button labels and links, site-wide SEO, admin-added videos, per-video overrides and deletes over the built-in catalog, and category/model/channel/tag additions, renames and deletions. CSV-imported videos are stored here as admin-added videos; an empty CSV cell is stored as null and the public site hides that field. Embed links the owner enters (YouTube, Vimeo, direct media files, generic iframe sources) are played back in a 16:9 player on the video page.

No third-party data sources are fetched at runtime.

Taxonomy bulk delete (added 2026-11-26): the admin Categories / Models / Channels / Tags lists now have the same bulk pattern as Videos — a per-item checkbox, a "Select all <list> (N)" toggle for the current tab, an "N selected" count, and a delete bar that requires an explicit "Confirm delete N …" before committing. Switching tabs clears the selection.

Embed playback note (verified 2026-11-26 against the owner's imported catalog): the admin state's 197 added videos all embed `https://www.freepornvideo.sex/embed/<id>` (a KVS player). That host's file endpoint (`/get_file/…`) only serves the video when the request carries the session cookies the embed page set — the same signed file URL returned 403 without those cookies and 302 with them, from any referer — so browsers/webviews that block third-party cookies in cross-site iframes showed the player shell but never played the file. Fix: the `resolveEmbedFile` action fetches the embed page server-side with its own session, follows the one gated hop, and returns the storage URL it redirects to; that URL was verified to answer 206 video/mp4 (with Range support) from a separate cookie-less request, and the video page plays it in a native in-page `<video>` player. If resolution or the file fails, the player falls back to the source iframe plus an "Open the player in a new tab" bar. Watch-page links (`/xxx/<id>/…`) are converted to `/embed/<id>` in `resolveEmbed`.

Full SEO (added 2026-11-26): three layers. (1) Static baseline in `client/index.html` — title, meta description/keywords, robots, rating, theme-color, Open Graph + Twitter card defaults and a WebSite/Organization JSON-LD graph, matching the admin SEO defaults. (2) Dynamic per-view SEO in the App: one effect derives each view's own meta description (a video's admin SEO description/description wins, else one is composed from its title, category, model and tags; listings compose from their name and live video count; index pages from live taxonomy counts), Open Graph (og:type video.other on video pages, og:image from the video's thumbnail) and Twitter cards, a canonical link for indexable views, a robots directive (noindex for admin, auth, history, profile, search results, 404 and the generated files), and per-view JSON-LD — VideoObject (thumbnail, uploadDate from the video's day count, ISO-8601 duration, embedUrl, view-count InteractionCounter, model as actor) + BreadcrumbList on video pages, ItemList + BreadcrumbList on category/model/channel/tag/feed pages, WebSite (with SearchAction) + Organization on home. The document-title effect covers every view including the generated files. (3) Dynamic sitemap & robots: `buildSitemapXml` / `buildRobotsTxt` generate both from the live effective catalog (built-in + admin-added − deleted), so new videos/taxonomy appear automatically, with per-video lastmod from its day count. They render as preview pages at `#/sitemap.xml` and `#/robots.txt` (with Download/Copy buttons) and are downloadable from the admin panel's SEO section, which shows the live URL/video/taxonomy counts. Note: this runtime serves a single HTML entry, so the sitemap/robots are generated in-app rather than served as separate static files at the domain root.

Robots/sitemap crawler fix (2026-11-26): the owner reported both files were useless to crawlers, and both reports were correct. (a) robots.txt: in robots.txt syntax `#` starts a comment, so each old `Disallow: /#/…` line was parsed as `Disallow: /` — six lines each blocking the entire site — and the `Sitemap:` line's fragment was stripped, pointing at the page itself. `buildRobotsTxt` now emits no `#` at all: just `User-agent: *`, `Allow: /` and a fragment-free `Sitemap: <root>sitemap.xml`. Private views are hash routes (never sent to a server, so robots.txt cannot disallow them); they stay out of the index via the existing per-view noindex meta. (b) Sitemap/canonical/OG/JSON-LD URLs: every published URL used to be a hash URL (`…#/video/…`), which crawlers strip to the single root URL. All of them now use fragment-free path URLs under the site root via the `publicUrl`/`siteRoot` helpers (sitemap `<loc>`, canonical link, og:url, VideoObject/BreadcrumbList/ItemList/WebSite URLs, and the static JSON-LD baseline in index.html). To make those path URLs actually open the named page, the app resolves them on load: `pathRoute()` reads the trailing pathname segments (only sitemap-published route shapes; admin/login/signup stay hash-only) and translates them into the matching hash route when no hash route is set.

Full-width player & fullscreen (changed 2026-11-26): the video-page player (EmbedPlayer and the catalog art player) now sits ABOVE the two-column grid, spanning the full width of the page container at 16:9, and bleeds edge-to-edge on phones (-mx-4, square corners; sm+ restores the inset rounded frame). Fullscreen is the site's own button, not the embed's: EmbedPlayer overlays an expand/compress button (top-right of the player box) that calls requestFullscreen() on the player box itself — so it works identically for the native <video> and the sandboxed fallback iframe, whose own fullscreen control can appear disabled — tracks fullscreenchange for its icon/label, exits on a second press (ESC also exits natively), and falls back to the video element's webkitEnterFullscreen on iPhones where element fullscreen is unavailable. The catalog art player's existing Fullscreen button now also exits when already fullscreen. `.pv-fs:fullscreen` in theme.css zeroes margin/radius in fullscreen.

Fullscreen inside the app frame (fixed 2026-11-26, after the owner reported again that the video "doesn't get big"): the earlier fix verified in the audit browser, but the published site runs inside the Muse app's frame, and a frame that does not grant the fullscreen permission makes every `requestFullscreen()` reject — the old handler then only tried iOS's `webkitEnterFullscreen`, so on other devices the button did nothing at all and the video never enlarged (the same policy greys out the native controls' own fullscreen button, the owner's original report). Both players (EmbedPlayer and the catalog art player) now share a `usePlayerFullscreen` hook whose toggle walks a ladder: standard `requestFullscreen` on the player box → `webkitRequestFullscreen` → the iPhone video element's `webkitEnterFullscreen` → an in-page expanded mode (the box becomes `position: fixed; inset: 0; height: 100dvh` at z-85 with body scroll locked), which needs no permission and always fills the screen the app gives it. The same button (compress icon while big) or Esc exits either mode, and opening another video collapses the art player's expanded mode.

Thumbnail placeholder (changed 2026-11-26): the `Thumb` component tracks its photo's load state. Until the photo loads, the tile shows the site name as its placeholder — the logo lockup (pink "PULSE", heart mark, white "VIDEO", Archivo black, sized off the tile width via container units) centered over the tile's gradient art. The photo fades in over it on load; a video with no photo, or one whose photo errors, keeps the name — never an empty black box.

Fullscreen control placement (changed 2026-11-26, per the owner's screenshot circling the native control-bar button): the floating round expand button at the player's top-right is removed entirely — fullscreen now lives only in the bottom control bar. The native `<video>` no longer uses the browser's built-in `controls` (whose fullscreen button, bottom-right next to the volume icon, is greyed out by the app frame's fullscreen policy and cannot be wired to anything); EmbedPlayer renders its own control bar instead — play/pause, current/total time, mute + volume slider, a click-to-seek progress bar with knob, and at the bar's right end, next to the volume control, the fullscreen button wired to the same `usePlayerFullscreen` ladder (real fullscreen first, in-page expanded mode as fallback), switching to the compress icon while big. A white circular play button sits at the player's center while paused, and tapping the video toggles play/pause. The fallback iframe gets the same treatment: no floating button, and a click-through bottom bar over the iframe whose only control is the same fullscreen toggle at its right end (the embed's own play/volume controls stay inside the iframe), so no player ever shows two fullscreen buttons and iframe videos keep a working fullscreen control.

Admin authorization — server-side check (changed 2026-11-26, per security review): the admin code and a token-signing secret now live only in `server/src/actions.ts`; the client bundle contains neither (the literal was removed from App.tsx entirely, including the old `#/[ADMIN_CODE]` route, comments and panel help text). Flow: typing the code into the site search box (or a same-origin parent-page fragment) sends the text to the new `verifyAdminCode` action; on a match the server returns a 12-hour HMAC-SHA256-signed token, kept in sessionStorage (`pv-admin-token`). `saveAdminState` and `resetAdminState` now require that token and re-verify it server-side on every call (`requireAdmin`), so the panel route alone grants nothing. The panel's hash route is now `#/panel` and only restores a session whose token this browser already holds. `getAdminState` deliberately stays readable without a token: its payload is exactly the content the public site itself renders (texts, catalog, SEO), so reading it exposes nothing the homepage does not already show. The owner's access method is unchanged — same code, typed in the same search box; there is still no separate password, by the owner's choice.

Player loading spinner & on-screen quality settings (added 2026-11-26): the native player shows a rotating spinner (`PlayerSpinner`, `.pv-spinner` in theme.css) until playback actually starts and again whenever the video stalls to buffer — driven by the element's waiting/playing/canplay events plus a `started` flag so the untouched poster + center play button never sits under a spinner; the resolving state and the fallback iframe's not-yet-loaded state show the same spinner instead of the old "Loading player…" text. A gear ("Quality settings") button now sits in the player's own control bar, left of the fullscreen button, whenever the embed offers both streams (`hdAvailable`); its menu (Fast · <label> / HD · Original, check on the active one) drives the exact same `quality` state as the pills under the player, so both controls stay in sync and a switch keeps the viewer's position via the existing pinned-stream/resume path.

Thumbnail placeholder — white + logo only (changed 2026-11-26, superseding the gradient-art placeholder described below): the `Thumb` tile no longer renders the gradient background or the `Motif` SVG art before the photo loads. The placeholder is a plain white (#fff) tile with only the site logo centered on it (pink PULSE, heart, black VIDEO — black so it reads on white). Playback speed & stability (fixed 2026-11-26, after the owner reported slow playback and the page suddenly throwing him back home): measured on the owner's catalog, the embed's main `video_url` file is the full-quality original — 261 MB, 280 MB, 332 MB and 3.67 GB on the four videos sampled — while every embed page also carries a `video_alt_url` 480p encode of 66–183 MB (~4–20x smaller) from the same storage hosts. `resolveEmbedFile` now resolves BOTH gated hops in parallel and returns `{ fileUrl, hdFileUrl, fastLabel }`: `fileUrl` is the fast alt stream the player starts with, `hdFileUrl` the full-quality original, `fastLabel` the alt's own label ("480p"). The player shows a Fast · 480p / HD · Original toggle under the player when both exist; switching keeps the viewer's position and play state. The playing URL is pinned in component state: likes/saves/history saves invalidate all queries server-side and each resolve mints a fresh signed URL, so feeding refetch results straight into `<video src>` used to restart playback mid-watch — a refetch may now replace the pinned URL only on a quality switch or on the single retry after the pinned file errors (signed URLs expire), and that retry resumes at the same timestamp before any iframe fallback. The fallback iframe for this host is sandboxed (`allow-scripts allow-same-origin allow-presentation`, no top-navigation/popups) so the embed's ad scripts can no longer navigate the viewer off the video page.

XNXX embeds — "Blocked content" fix (2026-11-26): the owner added a video with an `xnxx.com/embedframe/<id>` embed and its player showed "Blocked content. All resolutions playable (added 2026-11-26, per the owner: "সকল রেজুলেশনে ভিডিও প্লে হবে"): `resolveEmbedFile` now returns a `streams` list — every stream the source actually publishes for that video, lowest first, each with the source's own label and an `hls` flag; the player's gear menu and the pills under the player list exactly that list, and switching keeps the viewer's place via the pinned-stream/resume path (selection is by label, which is stable across re-resolves while signed URLs rotate). XNXX publishes two MP4s (240p/360p on the owner's video) PLUS an HLS master playlist (`setVideoHLS`) whose variants run 250p/360p/480p/720p/1080p; the resolver parses the master playlist server-side and merges both into one ascending list (the MP4 wins at a shared height), so the XNXX video's menu is 240p · 250p · 360p · 480p · 720p · 1080p. The playlists and their .ts segments answer with `Access-Control-Allow-Origin: *` (verified), so playlist streams play in the same native player — native HLS in Safari, hls.js (bundled dependency, loaded on demand) elsewhere. A–Z review round 2 (2026-11-26 evening, at the owner's request — full-site check, fix what's found): verified live against the owner's real catalog state (all 264 built-in videos deleted by the owner in admin; 198 imported videos — 197 freepornvideo + 1 XNXX; both hosts re-tested through `resolveEmbedFile` and resolving correctly, XNXX → 240p fast + 360p HD, freepornvideo → 480p fast + HD original; admin code flow re-tested: wrong code refused, correct code issues a token). Bugs found and fixed:
- HTML entities in imported text: 98 of 198 imported descriptions contained literal `&#039;` / `&amp;` sequences that React rendered verbatim ("wife&#039;s … babe &amp; her husband") on the video page, in search and in SEO descriptions. `adminToVideo` now runs every text field (title, description, creator, category, channel, tags, SEO fields) through `decodeEntities` (numeric + named entities, `&amp;` decoded last), so one decode at the data boundary fixes every surface including the sitemap and JSON-LD.
- The XNXX video's thumbnail URL is a video file (`…/preview.mp4`): an `<img>` can never render it, so its card sat on the white logo placeholder forever, the player poster was invalid, and og:image pointed at a movie. `Thumb` now plays video-file thumbnails as muted looping `<video>` previews; `EmbedPlayer` uses the thumbnail as poster/backdrop only when it is not a video file; og:image and the VideoObject thumbnail list skip video-file thumbnails.
- Admin panel data-loss race: the panel could mount on the built-in default state before `getAdminState` returned (e.g. reloading at `#/panel` with a session token), and any save in that window would have overwritten the owner's whole saved state — all 198 imported videos — with defaults. The panel now mounts only after the admin query succeeds; until then a loading screen (or an error screen with retry, panel kept closed) stands in.
- Home "Popular models" showed the 12 built-in demo creators, all "0 videos", while the one real model was buried at the end of the list; home "Channels" likewise listed 8 channels at "0 videos". `buildEffective` now sorts creators and channels by video count (stable), the home models strip and channels section list only entries that have videos, and each section hides entirely when none qualify. The Models/Channels tabs still list everything, busiest first.
- Home category chips were dead ends: they listed the first 11 built-in categories and the Latest filter matched only `video.category`, so every chip showed "No videos in this category yet" for the owner's catalog. Chips are now the busiest categories that actually have videos, and the Latest filter uses the same category-or-tag rule as category listing pages, so chip results and listing counts agree.
- "Because you watch Uncategorized": when the last watched video is an import with no category, the section now names its first tag instead of "Uncategorized", and its list matches by category or tag.
- Listing empty state no longer says "in the demo catalog"; the Models page clamps its page number like listings do, so a shrunken catalog can't leave it on an empty page.

Center-button resume fix + fullscreen auto-rotate (2026-11-26, per the owner: "পস বাটন মধ্যখানে যেটা আসে সেটায় ক্লিক করলে রিসোম হয় না" and "স্কিন বড় করলে অটো রুটেট হয়ে শুধু ভিডিও প্লে হবে"): three click-path defects fixed.
